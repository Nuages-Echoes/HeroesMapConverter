1d-note. How events/messages convert today (evidence: h3decoder.py,
    unified.py, a real conversion of "all for one.h3m"):
  * h3m parse: class-26 ground event payload -> objects.eventMetadata[<id>]
    (message, guard, experience, mana, morale, luck, resources x7,
    primarySkills x4, secondarySkills, artifacts, spells, creatures,
    players mask, applyToComputer, removeAfterVisit); the map-level Events
    section -> top-level dailyEvents[] (name/message/colors/firstDay/
    repeatPeriod/resources). Signs/ocean bottles (59/91) -> signMetadata,
    seer huts (83) -> seerMetadata, witch huts (113) -> witchhutMetadata,
    scholars (81) -> scholarMetadata, shrines (88-90) -> shrineMetadata,
    pandora (6) -> pandoraMetadata. In objects.tiles the object itself keeps
    {id, group, index, sprite, class, subclass} (26/59/83/91/93/113 all land
    in group ADVENTURE_MISCELLANEOUS).
  * unified -> .map: the event object is emitted under the generic
    HOMMOE_GROUP_TO_SID fallback sid ("windmill") + a propEntities row
    {type:0, id, sid:"event_<id>"}; _hommoe_generate_scripts writes one
    commentAiData quest "event_<id>" with an ObjectInteractionAfter
    trigger on entity "event_<id>" (repeat = isRecurringEvent) and actions
    from _hommoe_event_actions: message -> Print, resources -> GiveRes,
    mapped artifact -> GiveItemHero [sid,""], mapped skill -> AddSkillAll;
    monster/primaries/morale/luck/mana and unmapped artifact/skill ids go
    ONLY into the trigger comment (lost as data). dailyEvents -> quests
    "daily_event_<i>" with StartTurn [week,day] + Print/GiveRes.
  * .map -> unified: objects come back raw (sourceSid + all prop rows);
    dialogQuestData/commentAiData are carried raw under unified["scripts"]
    AND decoded by _hommoe_quests_to_events for our own generated sids only
    ("event_<id>" ObjectInteractionAfter entities -> objects.eventMetadata
    + class 26 on the object; "daily_event_<i>" StartTurn quests ->
    dailyEvents). Native OE quests on arbitrary entities stay raw only.
    The h3m writer gained a matching "event" encoder branch (payload
    field-for-field verified against the parser for AB/SoD and RoE widths).
  * OE-side candidates in Core.zip for the remaining 1d classes:
    scroll sids scroll_box / enchanted_scroll_box / mythic_scroll_box
    (6_artifacts.json) for h3 93; shrines altar_of_magic_1-4 already emit
    for 88-90; random-* spawn sids exist; NO stock sign / seer hut /
    witch hut / quest guard / random dwelling object (checked all

1d-note2e. Random dwellings 216/217/218 + dwelling player links -

  * Forward (unified_to_hommoe): a 216/217/218 object resolves to a fixed
    barracks_<faction>_<tier> sid - faction from castle_absodId (the

1d-note2c. "Linked to a player" option - YES, OE has one: the
    objectsProperties.propOwners table, rows {type, id, owner} joined to
    any object (type 0) or zone (type 1) by id. Evidence:
    - reference map-parser.ts:213: propOwners?: Array<{type?, id?,
      owner?}> with the comment "Explicit player-index ownership
      override. -1 observed meaning neutral/unowned."
    - reference map-write.ts:1482-1488: for a hand-placed random-city,
      "Without a propOwners row GME read the city as Player 1's and
      wrote owner 0 back on save" - so a row is REQUIRED to say "None";
      map-write.ts:1499 upsertPropOwner() ("Set (or create) the
      propOwners row of an object: the player it belongs to"); the
      random-hero default row is tryAppendRow('propOwners',
      {type:0, id:newId, owner:1}); map-save.ts:457-461 verifies an owner
      edit lands in the rebuilt propOwners table.
    - INDEXING SUBTLETY: propOwners.owner is 0-BASED (stored 0 = Player
      1, -1 = None) - MapGridCellContent.tsx:777 comment: "propOwners
      counts players from 0, so stored 0 is the Player 1 GME shows,
      while Block 1 spawns and the hero code above start at 1."
      Block 1 spawns[].owner and propSpawns.owner are 1-BASED
      (1 = Player 1). extract-oe-corpus-raw.ts:49-55 confirms
      propSpawns.owner (player starts, city-spawner/hero-spawner only)
      and propOwners (neutral-object ownership override) are two
      separate tables.
    - reference h3-import: ownership.ts renumbers the H3 owner byte
      (0-7, 255 = neutral) into COMPACT 1..N owners with the human
      always at owner 1 (1-based, used for spawns[]/propSpawns);
      convert-h3m-to-map.ts:709 writes propOwners {type:0, id} (owner
      key absent) for neutral/unowned towns.
    - GME UI: the random-city cell inspector (MapGridCellContent.tsx)
      exposes owner options [-1, 0..playersCount-1] = None / Player 1..N.
    - real test maps: only Broken_Alliance.map carries propOwners rows:
      3 rows, all on random-city objects, all owner:-1 (neutral).
      c_M1, all_cats_go_to_heaven, olden_era_template and
      synthetic_oemap_4blocks have none.
  Consequence for h3 216/217/218 (their payload carries an owner u32,
  0xFF = none - reference h3m-object-walk.ts:444-455 skipRandomDwelling
  parses it): IF they are ever converted to an OE barracks_*, the h3
  owner would map to a propOwners row on the emitted object written
  0-BASED (h3 owner byte 0-7 -> stored owner 0-7; 0xFF none -> -1),
  NOT to propSpawns (that table is only for player starts). Note the
  reference's own importer skips 216-218 entirely, so there is no stock
  precedent to copy for this field.

1d-note2d. "Can an OE dwelling be linked to a PLAYER (who has a faction)?"
    - YES. Two independent pieces of local evidence:
    - Format: propOwners is a GENERIC per-object table, not city-only -
      reference map-parser.ts:213 has no object-type restriction, and
      map-extract.ts:288-294 joins propOwners rows to ANY object
      (type 0) or zone (type 1) by id; the map-save.ts 'setObjectOwner'
      edit (line 229-230) is generic over entityType. In the reference
      editor UI the owner dropdown is only rendered for random-city /
      random-hero (MapGridCellContent.tsx:777, 844), and among the 5
      input/ test maps only Broken_Alliance.map carries propOwners
      rows (3x random-city, owner:-1) - but nothing in the schema or
      the writer restricts it to those sids; barracks templates
      themselves carry no owner (barracks.json is fixed
      fraction/tier/units), so ownership is per-instance = a propOwners
      row. Absence semantics: without a row GME reads a random-city as
      Player 1's (map-write.ts:1482); other objects (mines, barracks)
      default to neutral - so for a barracks: no row = unflagged,
      owner 0..N-1 = flagged by Player N+1, -1 = explicitly neutral
      (propOwners.owner is 0-BASED, see 1d-note2c).
    - Game mechanics: Core.zip Lang tutorial_M_11_1/2/3 - "Some
      interactive objects on the map have an owner - the player who
      last interacted with them", marked with a flag colored by the
      controlling player, "Ownable objects include cities as well as
      other key structures, such as:" - and tutorial_M_11_5:
      "Creature dwellings - ... While flagged, these dwellings
      passively increase the weekly growth of the corresponding
      creatures in all your cities." (+ tutorial_C3_3: "Your flag must
      be active at the beginning of the week for this growth bonus").
      That bonus is exactly the cityUnitsIncrementFromBarrack bonus on
      every barracks_* template in DB/objects_logic/hires/barracks.json
      ("This city's dwellings produce +{2}% units"). So in OE a dwelling
      is flaggable by a player, and the map-file record of that initial
      owner is the propOwners row.
    - H3 side has the same link: h3m-The-Corpus.txt - META_OBJECT_
      DWELLING / DWELLING_ABSOD / LIGHTHOUSE / RESOURCE_GENERATOR /
      SHIPYARD all carry [uint32] owner (0xFF none) (our h3decoder maps
      classes 17/18/19/20/42/87/53 to kind 'ownable' ->
      ownable_metadata[oid]['owner']), and the random dwellings
      216/217/218 carry owner u32 as their FIRST payload field
      (0xFF none; h3m2json maps it to the player list) - currently
      parsed but discarded (h3decoder.py randomDwelling branch).
    - Converter consequence: h3 dwelling owner (color byte 0-7,
      0xFF none) <-> propOwners row on the emitted OE barracks, after
      the compact player renumbering of 1d-note2c (h3 color c ->
      final 1-based owner o -> stored 0-based owner o-1; 0xFF -> -1).
      Reverse: OE propOwners owner o -> h3 owner byte via the inverse
      renumbering, -1 -> 0xFF. So a random dwelling's h3 "owner" can be
      preserved on an OE barracks via propOwners - but note OE owner
      means "flagged by" (drives the city growth bonus), while h3 216-
      218 faction alignment uses castle_absod_id/town bitfield instead
      (see 1d-note2b): the two links are different fields on both
      sides, dwelling->city does not exist in OE, dwelling->player does.

4. Lossy-by-design collapses (converted, but not 1:1)
------------------------------------------------------------

  - Scenery sprite variants -> one OE sid per family/biome
    (e.g. all pine variants -> pinetree_1 / pinetree_snow_1); the way back
    recovers the family, not the exact variant.
  - Specific H3 artifacts -> OE random-item (see 3a); random artifact
    classes 65-69 -> random-item + rarity row.
  - Fixed and random monsters -> OE random-squad with a propSquads /
    propRandomSquads row (unit sids + tier kept; H3 quantity split lost).
  - Towns and heroes -> OE city-spawner / hero-spawner: the H2 town race /
    hero class is not kept per object.
  - Roads and rivers are not OE objects: they live in the terrain layer
    (roadsMap bitfield, rivers node lists).
  - H3 battlefield terrains (21/46/223-231 except 141) -> OE tile biome
    repaint (user mapping, section 1c); the way back gives the plain
    biome, never the magical-terrain object.
  - H3 Event / Sign / Seer Hut / Quest Guard -> OE quest script triggers
    when the metadata fits: message -> Print, resources -> GiveRes,
    artifact -> GiveItemHero, skill -> AddSkillAll/AddSkillHero.
    Monster rewards, stat bonuses and unmatched artifact/skill ids are
    kept only in the trigger's comment field.
  - Den of Thieves AND Cover of Darkness both -> insaras_eye;
    Refugee Camp / Freelancers Guild / Mercenary Camp -> mercenary_guild.
  - OE _upg vs _upg_alt: both reverse to the same H3 creature id; forward
    (H3 -> OE) picks one at random, so .map output is non-deterministic
    for upgraded units.
  - Player colors: OE colorId is -1 in all real maps, so the color is
    assigned from the spawn order (first 6 = H2 order); the real color
    table lives in Core.zip and is not extracted yet.

5a. Container header (hommoedecoder.py write_hommoe / unified_to_hommoe):
  * headerHash: CONFIRMED opaque identity, no algorithm exists in either
    reference. map-editor-json-tool map-write.ts:18-24 brute-forced
    md5/sha1/sha256/sha512 over every plausible block combination - no
    match; map-write.ts:2518-2545: resaving an UNCHANGED map through GME
    produces a brand-new hash, so it is not a content checksum but a
    per-map identity the game keys map recognition on (a fixed cloned
    value makes maps collide and the game silently refuses to select
    them - confirmed via real player.log testing); the reference mints
    crypto.randomUUID().replace(/-/g,'') (generateMapHash, line 2544).
    The vs-code-inspector (docs/map-format.md) independently says the
    32-byte identifier is "shared between the samples and its meaning is
    unresolved" and validates /^[a-f0-9]{32}$/i (parser.js:86). headerHash
    is ALWAYS equal to scenario.hashSum in every sample. Note: our
    input/olden_era_template.map IS the reference's bundled
    src-tauri/resources/template.map (same headerHash
    11868446b59baaea451add92e46796d4, version 0.80.47, separator 05 00).
    IMPLEMENTED: the writer now mints a fresh uuid4().hex per h2/h3 ->
    .map output and sets hashSum equal to it (was the "0"*32
    placeholder); .map -> .map stays byte-exact via raw passthrough.
  * version: just the game version that wrote the map - 0.72.30 (3 of
    our real maps), 0.80.47 (template), 0.82.08 (inspector's Dia.Rush
    samples + our synthetic map; inspector parser.js:89 warns on any
    other version). Writer keeps HOMMOE_DEFAULT_VERSION "0.72.30"
    (majority of real samples); KNOWN_VERSIONS lists all three.
  * separator: semantics nailed by the reference - map-write.ts:129-134,
    157-159: SCRIPTS_FLAG = 0x08, "Block 4 is only read when bit 0x08 of
    the first separator byte is set: every shipped map with scripts has
    0d 00, every 3-block map 05 00" (ensureScriptsBlock ORs the bit in).
    The inspector's STDU fork documents the same 05 00 / 0d 00 pair. Our
    writer derives [0x0D,0]/[0x05,0] from the block count - equivalent.
    trailingData is 0 bytes in all 5 test maps and both Dia.Rush samples
    ("both samples end immediately after the fourth JSON object").
  * gzip header: single gzip stream, magic 1f 8b (inspector
    parser.js:34); real maps + template all FLG=0 MTIME=0 XFL=0 OS=10 -
    exactly our write_gzip canonical header; the synthetic map (XFL=2
    OS=3) keeps its own via gzipHeader passthrough. No gap.
