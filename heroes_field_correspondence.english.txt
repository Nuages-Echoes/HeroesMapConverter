   ╔╦╦╦════════════════════════════════════════════════════════════════════╦╦╦╗
   ║║║║  Unified JSON / FH2M / H3M / .map value correspondences            ║║║║

   Each table below lists the concrete values of one field in the four
   formats: the value as it appears in the unified JSON files
   (outputunified/), its equivalent in the .fh2m files (as parsed by
   h2decoder.py / stored by the fheroes2 engine), its equivalent in the
   .h3m files (as parsed by h3decoder.py), and its equivalent in the
   Olden Era .map files (parsed by hommoedecoder.py, "hommoe" source
   game) in the last "HOMMOE (.map)" column. UNDEFINE means the value
   has no direct or obvious equivalent in that format; an empty HOMMOE
   cell means the conversion is not known yet.

   The Olden Era structures that have no row in the tables above (OE
   hero sids, scripting blocks, object placement model, per-tile
   layers...) are documented in the "Olden Era (.map / hommoe)
   specifics" section at the end of this file.

   FH2M values marked with an enum come from the fheroes2 source code;
   the number in parentheses is the raw value stored in the file.

   The H3M Sand terrain converts to the Heroes II DESERT terrain
   and back (the unified value is "Desert"); the Heroes II BEACH
   terrain converts back to the H3M Sand terrain (the unified
   "Beach" value). "Sand" is not a unified terrain value anymore.
   sourceTerrain keeps the raw value: "terrain:<imageIndex>" for FH2M
   (e.g. "terrain:92"), the terrain name for H3M (e.g. "Snow").

   Per-tile fields kept for a faithful round-trip:

| sourceRiver / sourceRiverProperties | UNDEFINE (rivers are   | River Type / River Properties       | rivers[] overlay { sid, randomSeed, nodes: [{ n, s, isWaterfall }] } (sparse node list; river tiles do NOT set waterMap) |

   For FH2M sources the per-tile h3m fields are computed from the
   neighbors, not copied:
   - Mirroring keeps the fh2m terrainFlags mirror bits (0x01/0x02) and
     adds the coast bit 0x40 on non-water tiles adjacent to water (every
     such tile has it in the real maps); road tiles also get the road
     mirror bits 0x10/0x20.
   - Terrain Picture of coastal tiles comes from coastal_link.json:
     each coastal tile is keyed by the mask of its neighbors on the
     other side of the coast (N,NE,E,SE,S,SW,W,NW, '+'-joined) and mapped
     to the h3m (picture, mirroring) used in the reference maps, for
     water tiles (border sprites 0-19), Sand tiles and normal land
     tiles (coast sprites 24-39). The table was learned from
     input/*.h3m; see coastal_tiles_h2_h3.md (Tableau 3) for the H2->H3
     link per tile type.
   - Road Properties of road tiles comes from road_link.json: keyed by
     the cardinal (N,E,S,W) mask of neighboring road tiles, mapped to
     the h3m road sprite (lines 10/12, end caps 14/15, corners 0-3,
     T junctions 5-9, cross 4) learned from input/*.h3m.
   - River Type / River Properties of river tiles: the type comes from
     the tile terrain (Lava -> Lava, Snow -> Icy, Dirt -> Muddy, else
     Clear) and the sprite from river_link.json, keyed by the cardinal
     mask of neighboring river tiles (lines 9/11, end caps 9-12,
     corners 0-3, T junctions 5-8), with the river mirror bits
     0x04/0x08 in Mirroring.

The fh2m metadata maps are fully carried into the unified format:
every entry keeps its raw fh2m fields (for the byte-perfect fh2m
round-trip) and gains normalized fields with readable names resolved
from the identifier tables in correspondence.py:

  builtBuildingNames / bannedBuildingNames (building bit flags),
  mustHaveSpellNames / bannedSpellNames (spells)
- heroMetadata army[] (monster, sourceMonsterId, count),
  artifactNames, availableSpellNames, secondarySkills[] (skill,

  portraitName (portrait:<id>, None for the default portrait),
  patrol (enabled, radius), progression (level, experience, mana;
  None keeps the game defaults)

  availableToHire[] (monster per dwelling tier 1-6, count; -1 keeps

  Spell Scroll reward, when the artifact is a Spell Scroll)

   spells or artifacts.

   Decorative objects (h3m -> fh2m): the decorative h3m classes
   (identified by the sprite families: AVLsh shrubs, AVLmt
   mountains, AVLf flowers, AVLca cacti, AVLtr trees, AVLr rocks,
   AVLdead dead trees, AVLlav lava lakes, AVLms mosses and so on)
   convert to representative Heroes II landscape objects through
   the H3M_DECORATIVE_TO_FH2M table (a shrub becomes a grass shrub,
   a mountain a medium mountain, a cactus a desert cactus, a dead
   tree a generic dead tree...). The tree classes refine the index
   through the def name (H3M_TREE_DEF_TO_FH2M_INDEX: palms -> 17,
   dead trees -> 24, log -> 25, stumps -> 26, single trees/conifers
   -> 7) so the variant, hence the sprite size, is
   preserved. The classes without a mapping stay
   dropped. The UNDEFINED_<class> objects stay in the unified JSON
   so future mappings can extend the coverage.

   Roads and rivers (h3m -> fh2m): the h3m format stores the road
   and river types per tile (Dirt/Gravel/Cobblestone roads,
   Clear/Icy/Muddy/Lava rivers); the Heroes II format places a ROADS
   or STREAMS object per tile whose index is the connection bitfield
   (TOP_LEFT=1, TOP=2, TOP_RIGHT=4, RIGHT=8, BOTTOM_RIGHT=16,
   BOTTOM=32, BOTTOM_LEFT=64, LEFT=128). The connections are derived
   from the neighboring tiles carrying a road/river. The road and
   river variants and the type distinction (all the h3m road types
   become the single Heroes II road, all the river types the single
   stream) are not carried.

   Conversion guards (h3m -> fh2m, unified_to_fh2m): a map with an
   underground raises 'Heroes of Might and Magic 2 ne permet pas de
   jouer avec le sous-sol, la carte X ne peut pas être convertie';
   a map with more than 6 available players raises 'Le nombre de
   factions est limité à 6 dans H2, impossible de convertir la carte
   X'.

   Cross-format object translation (h3m -> fh2m, main.py --target fh2m):
   placed objects are translated group by group when an fh2m
   equivalent exists; the others are dropped and their ids are listed
   under objects.dropped. The identifier pairs (creatures, artifacts,
   spells, resources) come from the tables in correspondence.py:
   - MONSTERS: h3m creature -> fh2m monster (index = monster id - 1),
     with the count, the after-defeat message and resources when
     present; creatures with no Heroes II equivalent are dropped
   - ADVENTURE_TREASURES: h3m resource -> fh2m resource object index
     (0 wood ... 6 gold)
   - ADVENTURE_ARTIFACTS: h3m artifact -> fh2m artifact (index follows
     the fheroes2 ADVENTURE_ARTIFACTS group order); random h3m
     artifacts (classes 65-69) become the fh2m random artifacts
     (group indices 91-95, one per class); artifacts with no Heroes
     II equivalent become the fh2m random artifact of the same
     Heroes III class through H3M_ARTIFACT_CLASSES (Treasure ->
     Random Treasure, Minor -> Random Minor, Major -> Random Major;
     the Relic map to the Random Major per user decision - Heroes II
     has no random relic)
   - KINGDOM_HEROES: h3m hero -> fh2m hero object (index = color * 7 +
     race from the hero pairing) with a full heroMetadata: name,
     experience, primary skills, secondary skills (converted through
     the secondary skill table; the skills with no Heroes II
     equivalent become the random skill, keeping their level), army
     (the first five non-empty
     creature slots), artifacts (worn slots and backpack through the
     artifact table), available spells (bitfield through the spell
     table) and patrol state; neutral heroes (owner 255) are prison
     inmates: they convert to the fh2m Jail object (ADVENTURE_MISC
     47), the Heroes II prison releasing the hero on capture;
     biography, face and gender have no Heroes II equivalent
   - ADVENTURE_MINES / ADVENTURE_DWELLINGS: translated with a
     capturableObjectsMetadata carrying the owner color (when the
     owner is a Heroes II color). The h3m class 53 mines convert to
     the fh2m mine index through h3m_mine_to_fh2m_index: the subclass
     gives the mine type, the def name gives the terrain appearance
     (read from the tile terrain when the def has no terrain variant,
     e.g. the sulfur mine), so index = appearance * 5 + resource for
     the resource mines, 40 + appearance for the abandoned mines and
     the sawmill/alchemist slots for subs 0/1. The h3m class 17
     dwellings convert back to the fh2m dwelling index through
     H3M_TO_FH2M_DWELLINGS (subclass = dwelling id; the elemental
     altars 7/13/16/47 go back to fh2m indices 22/21/23/24), other
     ownables fall back to index 0
   - KINGDOM_TOWNS: translated with the fh2m race from the h3m town
     type (see the town/race table above) and a castleMetadata
     carrying the custom name, the garrison creatures as defenders
     and the built/disabled buildings converted to the fh2m building
     flags (castle, tavern, marketplace, shipyard, mage guild 1-5
     and the generic dwellings with their upgrades; town halls, fort
     and citadel have no Heroes II equivalent). The fh2m town tile is
     the castle entrance, so the town is placed at the h3m instance
     coords + (-2, 0).
   - ADVENTURE_POWER_UPS: shrines are translated to the matching
     shrine circle (Incantation -> First Circle, Gesture -> Second
     Circle, Thought -> Third Circle); other power-up objects are
     dropped
   - ADVENTURE_MISCELLANEOUS: pandora boxes (h3m class 21 group)
     convert to the fh2m Sphinx object (index 31) like the seer
     huts: the guard message becomes the riddle (a default riddle
     when there is no guard), the answers stay empty and the
     artifact or resource bonuses convert; the other h3m bonuses
     (experience, mana, morale, luck, primary and secondary skills,
     spells, creatures) and the guard fight are lost. Seer huts
     (h3m class 62 group) convert to the fh2m Sphinx object
     (index 31): the riddle is the fixed 'Validez pour obtenir la
     recompense.' prompt with an empty valid answer. The reward
     converts when the fh2m sphinx supports it (an artifact or
     resources); the other h3m reward types (experience, morale,
     luck, primary and secondary skills, spells, creatures) are
     lost. A seer with no quest is dropped. Witch huts (h3m class
     113) and scholars
     (h3m class 62) convert to the fh2m Witch's Hut object (index 26);
     the fh2m format carries no per-hut metadata, the engine draws
     the secondary skill at game start (the h3m fixed skill and the
     scholar reward are lost). RoE witch huts carry no skill bytes:
     the decoder emits an empty witchhutMetadata entry so the
     object still converts. Mercenary camps (h3m class 51, no
     per-instance data) route through the interactive table to
     the fh2m Mercenary Camp (ADVENTURE_POWER_UPS 13). Garrisons (h3m class 35) convert to a
     monster troop: the highest level creature (the highest h3m
     creature id among the non-empty slots) becomes a placed monster
     with its count; a garrison with no creature, or whose best
     creature has no Heroes II equivalent, is dropped. Ground events
     (h3m class 26) convert to
     the fh2m event object (index 38) with a full
     adventureMapEventMetadata: message, player colors (the h3m
     player bitmask maps to the Heroes II colors; an empty mask means
     every player), resources, primary skills, experience, the first
     secondary skill (through the secondary skill table, the skills
     with no equivalent becoming the random skill), the first
     artifact (the Spell Scroll carrying its spell through the spell
     table) and the first creature; removeAfterVisit inverts into
     isRecurringEvent. Signs are translated with their message
   The remaining h3m groups (pandora boxes, shrines, seer huts, garrisons...)
   have no fh2m equivalent and are dropped. fh2m object groups that are
   pure landscape (ROADS, STREAMS, LANDSCAPE_*) exist only on the fh2m
   side.

   The creatures are grouped by faction: Faction 1 to 6 pair each
   Heroes II faction with its primary Heroes III counterpart, Faction
   7 to 9 pair the Heroes II factions with the Heroes III factions
   that have no Heroes II equivalent (Inferno, Fortress, Conflux),
   plus the neutral creatures. The third name in each group title
   is the Olden Era faction of the group, following the Races
   table above. Within a faction, each tier matches
   the H2 creatures with the H3 creatures of the same tier. The
   upgrade chains are written with '->' inside a cell. UNDEFINE marks
   a creature with no equivalent. The h3m random monsters are
   converted through their object class: Random Monster (any level),
   Random Monster 1 to Random Monster 4 (h3m classes 71 to 75 ->
   fh2m ids 67 to 71). The HOMMOE unit column gives the Olden Era
   display names (reference src/data/units.json); the underlying
   unit sids are kept in oe_object_correspondence.json
   (creature_equivalents).

   Olden Era units have two upgrades per tier where H3 has one:
   <base>_upg and <base>_upg_alt (e.g. esquire_upg = Guard Captain and
   esquire_upg_alt = Sun's Aegis; reference src/data/units.json). The
   HOMMOE unit column shows the base -> _upg chain. H3 -> OE maps an
   upgraded H3 creature to _upg or _upg_alt (chosen at random); OE ->
   unified maps both _upg and _upg_alt to the same H3 upgraded
   creature, since the _upg_alt variant has no H3 counterpart.

Olden Era (.map / hommoe) specifics
================================================================

   The tables above now carry a "HOMMOE (.map)" column with the Olden
   Era equivalent of each unified value (an empty cell means the
   conversion is not known yet). This section keeps only the structures
   that have no row in those tables. Sources: the local references
   (references/map-editor-json-tool,
   references/olden-era-map-vs-code-inspector) and the real maps in
   input/*.map; the object-level correspondence is data-driven from
   oe_object_correspondence.json and the no-equivalent list is
   no_olden_era_equivalent.english.txt.

   Container layout: a single gzip stream (magic 1F 8B; the real maps
   all use FLG=0, MTIME=0, XFL=0, OS=10, reproducible byte-for-byte)
   holding [varint len][32-hex hash] [varint len][version string]
   [2-byte separator: 05 00 = 3 blocks, 0D 00 = 4 blocks (bit 0x08)],
   then N blocks of [varint len + UTF-8 JSON], plus an optional opaque
   tail. Canonical block names: scenario, adventure, dialogQuestData,
   commentAiData. Blocks 3/4 are the scripting layer, carried verbatim
   in the unified "scripts" section; the optional same-name .json
   sidecar is the editor's trimmed copy of block 4.

Faction display names
----------------------------------------------------------------

   Display names verified against Core.zip localization via the
   reference's factions.ts: human->Temple, undead/necros->Necropolis,
   dungeon->Dungeon, nature->Grove, demons/demon->Hive,
   unfrozen->Schism, neutral->Neutral. FACTION_ORDER (game order):
   Temple, Necropolis, Dungeon, Grove, Hive, Schism, Neutral.

Heroes
----------------------------------------------------------------

   OE has its own 108 heroes (6 factions x 18), identified by sids of
   the form "<faction>_hero_<N>" (human_hero_1, necro_hero_1,
   demon_hero_1, dungeon_hero_1, nature_hero_1, unfrozen_hero_1; names
   from the reference's src/data/heroes.json, e.g. human_hero_1 =
   "Ister", demon_hero_1 = "Niev"). OE hero names do NOT match H2/H3
   hero names, so there is no per-hero correspondence: placed heroes
   are "hero-spawner" objects, the chosen hero is the spawns[].heroSid
   / propHeroes.heroSid field (empty = random/default). H2/H3 heroes
   keep their identity only through sourceHeroSid when the source is
   already a .map.

   Starting spells: each OE catalog hero def has fixed startMagics
   (Core.zip DB/heroes/**/*.json, startMagics[].sidConfig; 133 of 177
   hero defs have some - extracted to oe_object_correspondence.json
   "oe_hero_start_magics"); propHeroes rows reference catalog heroes
   only, so per-spawn custom spell lists do not exist in OE. Conversion
   (user decision): OE -> H3 rebuilds the SoD 9-byte spells bitfield
   from the hero's startMagics (exact for the 11 spell name matches,
   else a random same-rank spell); H3 -> OE drops a custom hero spell
   bitfield - the spawned OE hero gets its def's standard spells.

Loss condition
----------------------------------------------------------------

   Loss condition: OE has no structured loss list; "loseEverything" is
   the default unless the scripts use GameLose / SideLose actions
   (unified lossCondition.scriptHasLoseAction).

Per-tile layers
----------------------------------------------------------------

   Per-tile: sourceLevel = levelsMap (elevation tier, -1 = basin),
   sourceClimb = climbsMap (slope marker on the lower side of a level
   boundary), sourceRoadIndex = roadsMap (road TYPE id per tile, 0/1/2
   - not a direction bitfield like FH2M ROADS objects), rivers are a
   separate overlay: adventure.rivers[] = [{ sid, randomSeed, nodes:
   [{ n, s, isWaterfall }] }] (sparse node list, s = shape code 0-14;
   river tiles do NOT set waterMap). Kept raw in objects.sourceRivers.

Rumors / daily events / scripts
----------------------------------------------------------------

   OE has no rumors and no timed daily events. The unified "rumors" and
   "dailyEvents" lists are empty for hommoe sources; H2 rumors vanish
   and H2 dailyEvents / H3 timed Events convert to unified dailyEvents,
   which become OE quest triggers (StartTurn + actions) in block 4.
   The unified "scripts" section carries blocks 3/4 verbatim:
   scripts.dialogQuestData, scripts.commentAiData ({ comment, aiRolesId,
   counters[], interruptions[], quests[] }).

Objects
----------------------------------------------------------------

   Per-object correspondence (unified group/index or h3m class -> OE
   sid, both directions) is data-driven from oe_object_correspondence.json
   (see also no_olden_era_equivalent.english.txt for the types with no
   OE equivalent). OE placement: adventure.objects[] groups { sid,
   ids[], nodes[], rotations[], levels[] } (levels is a float column),
   adventure.squads[] for fixed squads, adventure.markers[] for editor
   zones, adventure.objectsProperties for per-instance rows (propSquads,
   propRandomSquads, propResParams, propRewardParams, propOwners,
   propPortals, propCities, propSpawns, propHeroes, propEntities, ...).
   Grid: node is flat row-major, x = node % sizeX, z = node // sizeX.
