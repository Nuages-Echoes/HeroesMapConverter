   /workspace/references/):
   - map-editor-json-tool (https://github.com/mimiasei/map-editor-json-tool):
     src/lib/map-parser.ts, src/lib/map-write.ts, src/lib/map-file.ts
   - olden-era-map-vs-code-inspector
     (https://github.com/IgorIziyoAlhasov/olden-era-map-vs-code-inspector):
     src/parser.js, docs/map-format.md

   A .map file is a single gzip stream (magic 1F 8B). All offsets and
   lengths below refer to the DECOMPRESSED bytes. The container is a
   sequence of length-prefixed chunks; there is no fixed chunk count:
   chunks are read until the end of the decompressed data.

   Gzip wrapper (observed identical on every sample, game-written and
   editor-written alike):
     2   magic 1F 8B, 1 byte CM=08, 1 byte FLG=00
     4   MTIME = 0 (little-endian)
     1   XFL = 00, 1 byte OS = 10 (0x0A)
     .   deflate stream: raw zlib (wbits=-15), level 6, memLevel 8,
         default strategy
     8   trailer: CRC32 of the decompressed data, ISIZE (mod 2^32)
   Recompressing the decompressed payload with those settings reproduces
   the original .map file BYTE-FOR-BYTE (verified on all samples with
   zlib 1.3.1), so write_hommoe() emits exactly that container.

   Notation:
   The first number in a line is the length of an element in bytes.

   1     { element length in bytes
   var   { unsigned LEB128 varint: 7 bits of value per byte, least
         | significant group first, high bit set = more bytes follow
   #     { a length-prefixed string: varint length, then that many bytes

████                          Container layout                           ████

 Length Description

   var   # Header hash: 1 length byte + the hash bytes. In practice a
         32-char lowercase hex digest (e.g. "11868446b59baaea...").
         The same digest is duplicated as block 1's "hashSum" field;
         the algorithm producing it is unknown, so both copies are
         preserved verbatim, never recomputed.
   var   # Version string, format "X.Y.Z" (observed: "0.80.47" on
         3-block maps, "0.82.08" on 4-block maps).
   2     Separator. First byte 05 (3-block maps) or 0D (bit 0x08 set:
         a fourth scripting block follows). Second byte always 00.
   var   # JSON block: varint byte length, then that many bytes of UTF-8
   *     JSON text (a leading UTF-8 BOM may be present). Repeated until
         the end of the decompressed data; usually 3 or 4 blocks. A
         zero-length block is an empty block. Block names below are
         canonical, assigned by position.
   ?     Optional opaque trailing bytes after the last block; preserved
         as-is by the parser/writer.

Validation (parse_hommoe, mirrors the reference parsers):
   - gzip: magic 1F 8B checked, header fields parsed (kept for byte-exact
     rewrite), CRC32/ISIZE validated by the decompressor. The inspector
     additionally caps the input at 32 MiB and the decompressed payload at
     64 MiB; parse_hommoe enforces the same limits (INPUT_LIMIT /
     OUTPUT_LIMIT) and rejects non-gzip files with a ValueError.
   - header hash: must be 32 hex chars (inspector: /^[a-f0-9]{32}$/i,
     hard error there; here a warning, value kept verbatim).
   - version: must match N.N.N (inspector hard error); known versions
     0.72.30 / 0.80.47 / 0.82.08, others produce a warning.
   - separator: must be 05 00 (3 blocks) or 0D 00 (4 blocks). The
     inspector hard-errors otherwise; map-editor-json-tool just skips
     the 2 bytes. Here an unknown separator is a warning, and the
     expected block count is compared with the actual one ("missing
     observed block ..." / "extra block(s) ..." warnings).
   - length prefixes of the hash and version strings: read as unsigned
     LEB128 varints here and in the inspector (src/parser.js
     lengthPrefix()); map-editor-json-tool (src/lib/map-parser.ts)
     reads a single byte instead - identical for every real map since
     both lengths are < 128, but a >127-byte hash/version would parse
     differently there.
   - blocks: each block's JSON is parsed after stripping a leading UTF-8
     BOM (map-editor-json-tool does the same); the raw text is always
     kept verbatim. The inspector requires each block to be a JSON
     object and hard-errors on invalid JSON; the editor tool falls back
     to {} with a warning. Here invalid/non-object JSON is a warning
     and the raw text is preserved (lossless round-trip).
   - adventure block structure: objects[] groups must have a string sid
     and parallel ids/nodes/rotations/levels columns of equal length,
     integer ids/nodes/rotations (levels is a float column on real maps,
     e.g. -1.5/0.5), at most 250,000 placements, propRandomSquads an
     array of rows with integer ids - the inspector enforces these as
     hard errors, here they are warnings. A truncated final block is a
     hard error for the inspector, an empty block for the editor tool;
     here it becomes a warning and the remaining bytes stay in
     "trailingData".
   All checks are reported in the "warnings" list of the parse result;
   hard errors (bad gzip, truncated header, varint overrun, size
     limits) raise ValueError.

████                          JSON blocks                                ████

 Block 1 "scenario" - lobby/scenario metadata. Known fields include:
   title, desc, gameMode, template, campaignInfo, difficulty tables
   (economicDifficulties, aiDifficulties, ...), spawns {
     playersCount,
     spawns[]: one entry per spawner object on the map (NOT one per
       player slot): owner, spawnType (0=Player, 1=Bot, 2=open slot),
       spawnPointType (0=City, 1=Hero), isCityDefined, factionSid,
       isHeroDefined, heroSid, colorId, isAlive, isLocked,
     takenHeroes
   }, banInfoData { bannedHeroes, bannedUnits, bannedMagics,
   bannedItems, bannedSkills }, hashSum, and more.

 Block 2 "adventure" - map data. Known fields include:
   fileMapName, mapName, mapDesc, mapNameFromLoc/mapDescFromLoc,
   sizeX_/sizeZ_ (map dimensions), then per-tile flat arrays indexed by
   "node" (see Grid indexing below): tilesMap (terrain type id per
   tile), waterMap (water material id, 0 = none), levelsMap (elevation
   tier: -1 = lowered, 0 = ground, 1 = heightened), climbsMap (ramp
   marker: set on the LOWER side of a levelsMap height boundary),
   roadsMap (0 = none, else road type id), customAreasPainting
   (player-region paint, empty array when unpainted), areas (RMG zones
   { id, nodes[] }), rivers [{ sid, randomSeed, nodes: [{ n, s,
   isWaterfall }] }] (sparse; river tiles do not set waterMap),
   objects[]: object groups, each { sid, ids[], nodes[], rotations[],
   levels[] } with the columns aligned by index (sid may be a string
   or an array of strings), squads[] (fixed squad placements, a
   SEPARATE id namespace from objects[]): { sid, ids[], nodes[] },
   markers[] (editor zone annotations): { node, id, sid, v },
   settings: game rules, including mapWinConditions[] (one entry per
   active win condition, keyed by typeWinCondition: 0 classic, 1
   desertion, 2 hero lighting, 3 capital hold, 4 guardian's demise,
   5 final battle, 8 city hold, 9 tournament; enum from the game's RMG,
   see the references). Loss conditions are not structured: the default
   is "lose everything", scripts can force one with GameLose/SideLose
   actions (block 4).
   objectsProperties: per-instance property tables keyed by
   (type, id), including propEntities, propsName, propHeroes,
   propCities, propSquads, propNoCombineGeometries, propSpawns
   (duplicated from block 1's spawns.spawns[], matched by owner),
   propPortals { targetIdx, isActive }, propRewardParams,
   propRandomSquads, propRandomHires, propActivations, propOwners,
   propMarkers, propActionsBefore, propActionsAfter.

 Block 3 "dialogQuestData" - dialog/quest shell:
   { dialogs: { lines: [] }, quests: { quests: [] } }.

 Block 4 "commentAiData" - scripting layer, present when the separator
   first byte has bit 0x08 set:
   { comment, aiRolesId, counters[], interruptions[], quests[] }.
   The game runs a map's quests from THIS block inside the .map, not
   from the sidecar .json.

   Field names vary slightly across game versions (e.g. 0.80.x uses
   sizeX_/sizeZ_ in block 2); the parser is version-agnostic and keeps
   the JSON blocks as-is.

████                          Sidecar .json file                        ████

   Next to a Foo.map, the map editor keeps an optional Foo.json: its own
   copy of the scenario scripting layer (counters, triggers, dialogs,
   localization). The game itself does not read it (quests are embedded
   in block 4 of the .map), so a .map file alone is self-contained.

████                          Grid indexing                              ████

   Tiles and objects are keyed by "node", a flat row-major tile index
   over a sizeX x sizeZ grid: X = node % sizeX, Z = node // sizeX
   (per the STDU fork's grid code, cited in the inspector's
   docs/map-format.md; the available samples are square, so the stride
   axis is not confirmed by them alone).
